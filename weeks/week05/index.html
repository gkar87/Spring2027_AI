Games as search

An opponent who is trying to make you lose.

Why games are a good testbed — and a misleading one

Good properties

  • The rules are exact, so there is no modelling ambiguity.
  • Win or loss is unambiguous, so progress is measurable.
  • The opponent provides an unlimited curriculum of hard cases.
  • Self-play generates its own training data.

Misleading properties

  • Perfect information and deterministic rules are rare in the world.
  • A game score is a single number, so the evaluation hides everything else.
  • Superhuman play does not transfer to open-ended tasks.
  • Games have no humans in the loop to harm — which is a large omission.

Keep both columns in mind. "It beat the world champion" is evidence about a narrow, well-specified problem — not a general claim about intelligence, and not a claim that module 15's questions are answered.

Formalising a game

Two-player zero-sum game

States S, a player to move in each, actions A(s), a result function, a terminal test, and a utility U(s, p) where one player's gain is the other's loss.

Assumptions made explicit

  • Perfect information — both players see the full state. Chess yes, poker no.
  • Deterministic — actions have single outcomes. Backgammon no.
  • Zero-sum — utilities are negatives of each other.
  • Rational opponent — they play to maximize their own utility.

What each assumption buys

Perfect information lets us search the true state. Determinism lets us compute a value instead of an expectation. Zero-sum lets one number describe both players. Rationality lets us model the opponent as a minimizer.

Remove rationality and minimax is too pessimistic: a random opponent is not out to get you, so expectimax is the right model.

Minimax: assume the worst, choose the best of it

V(s) = maxa V(Result(s, a))    if MAX to move
V(s) = mina V(Result(s, a))    if MIN to move
V(s) = U(s)    if terminal

The value of a state is what you can guarantee against an opponent who plays perfectly. It is not the value you expect to achieve against a weak opponent, and it is not an average over their mistakes.

§

Minimax is pessimistic by construction. That is a feature: it produces a policy that does not depend on the opponent blundering.

Minimax is correct and unusable

Minimax is correct and unusable
CompleteYes, if the tree is finite.
OptimalYes, against an optimal opponent.
TimeO(bm)
SpaceO(bm) with depth-first evaluation.

Chess has b ≈ 35 and games of about 80 plies. That is 35⁸⁰ ≈ 10¹²³ nodes. The observable universe holds about 10⁸⁰ atoms.

Three ways out, all used in practice

  1. Prune — alpha–beta removes branches that cannot matter.
  2. Cut off — stop early and estimate with an evaluation function.
  3. Sample — do not search the tree exactly; simulate instead (MCTS).

Every strong game engine uses at least two of the three.

§

The number 10¹²³ is not a motivation to write faster code. It is a proof that exact search is the wrong algorithm class for the problem.

Pruning and cutting off

The same answer with less work, and the price of stopping early.

Alpha–beta: the same answer, less work

Keep two bounds while searching: α, the best value MAX can already guarantee, and β, the best value MIN can already guarantee.

  • At a MAX node, raise α as you find better children.
  • At a MIN node, lower β.
  • If α ≥ β, stop: the remaining children cannot change the answer.
Why the prune is safe

Suppose MAX is choosing between branch A and branch B. While exploring B, MIN has already forced its value down to 2. MAX has already found 3 in branch A.

Whatever the rest of B contains, MIN will keep it at 2 or lower. MAX will never choose B. Every remaining node under B is irrelevant to the root value.

§

Pruning removes work, never information that mattered. That is why the returned value is identical, not approximate.

Best case halves the exponent; worst case does nothing

best case: O(bd/2) With perfect move ordering, alpha–beta examines about the square root of the minimax tree.

For chess that is the difference between 35⁸⁰ and 35⁴⁰ — still enormous, but inside the range where a cutoff search with a good evaluation function works.

With random ordering the gain is closer to b3d/4; with adversarial ordering, no gain at all.

Move ordering is the engineering

  • Try captures and checks first — they are most likely to be best.
  • Use the previous iteration's best move first (iterative deepening).
  • Keep a transposition table so repeated positions are evaluated once.

Every one of these is a heuristic about which move is likely best. Alpha–beta converts good guesses about ordering into exponential savings — the same theme as module 3.

Cutting off search creates the horizon effect

Real games are too deep, so we stop at a depth limit and apply an evaluation function — a heuristic estimate of the position's value. This is module 3's heuristic idea, applied to game states.

The evaluation should preserve the ordering of positions, not their exact values. A function that ranks well but is badly scaled is still useful.

Horizon effect

A bad outcome is pushed just beyond the search limit. The engine believes the position is fine because the loss occurs at depth 7 and it searched depth 6.

A concrete horizon failure

A queen is trapped and will be lost in five moves. Within a depth-4 search, the engine sees only that it can delay the loss by one move — so it does, and reports a better score. It has not improved the position; it has moved the disaster outside the window.

Quiescence search mitigates this: at the cutoff, keep searching only forcing moves (captures, checks) until the position is quiet.

Every cutoff search has a horizon. The only question is whether you have engineered around its worst cases.

Chance and sampling

Expectimax, Monte Carlo tree search and self-play.

Expectimax: when the world is random, not hostile

If an outcome is produced by chance — a die, a shuffled deck — model it with an expectation rather than a minimum. The agent then maximizes expected utility.

V(s) = maxa Σs′ P(s′ | s, a) · V(s′)

This is the Bellman equation of module 6, appearing early. MDPs and expectimax are the same idea with different bookkeeping.

Minimax is wrong for a random opponent

Against a die, minimizing assumes the worst face every time. That produces needlessly conservative play — the same error as planning for an adversary who is actually indifferent.

§

The model of the other agent is a design choice. Minimax for an adversary, expectimax for chance, and a mixture when the opponent is merely imperfect.

Monte Carlo tree search: sample instead of enumerate

  1. 1
    Selection

    From the root, follow child statistics until reaching a node not yet expanded.

  2. 2
    Expansion

    Add one new child for an untried action.

  3. 3
    Simulation

    Play to the end with a fast, dumb policy — random or nearly so.

  4. 4
    Backpropagation

    Update win counts along the path visited.

UCT = wi/ni + c·√(ln N / ni) exploitation term + exploration term

Why sampling beat search in Go

Go has b ≈ 250 and games around 150 moves. Minimax is not merely slow; the evaluation function is the real problem — nobody could write a good positional evaluator by hand.

Two properties made MCTS effective:

  • Anytime — it returns a usable move immediately and improves with more simulations.
  • No evaluation function — it uses game outcomes, which are exact.

The asymmetry that mattered

Chess engines were strong because humans could articulate what a good position looks like. Go players could not articulate it — the knowledge was tacit.

MCTS replaced the missing evaluation function with rollouts. That is a general lesson: when you cannot specify the objective, learn or sample it instead.

§

Pure MCTS was still not enough for superhuman Go. The breakthrough was combining it with a learned policy and value network — which is the next slide.

Self-play: the opponent becomes the curriculum

Policy network

Outputs a probability over moves. Used to narrow the tree instead of trying all 250 moves.

Value network

Predicts the game outcome from a position, replacing deep rollouts with one forward pass.

Self-play loop

Play against a previous version of yourself, label positions with the result, retrain, repeat.

This loop is a reinforcement-learning algorithm with a moving target: the data distribution and the policy co-evolve. It is also where the modern connection to module 13 begins — a preference model replacing a game result is a small change.

§

Self-play works when the environment can generate unlimited episodes and the reward is exact. Those conditions hold in games and almost nowhere else.

Key takeaways

  1. 1
    Minimax computes a guarantee, not an expectation.

    The value assumes a perfect opponent, which is a modelling choice.

  2. 2
    Alpha–beta is exact.

    It changes the work, never the value; its speedup depends entirely on move ordering.

  3. 3
    Cutoffs create horizons.

    Every evaluation function is a proxy, and every proxy can be gamed by delay.

  4. 4
    Sample when you cannot specify.

    MCTS replaced a hand-written Go evaluator with outcomes.

  5. 5
    Games are a narrow testbed.

    Exact rules and exact rewards are what make self-play work — and what the real world withholds.
