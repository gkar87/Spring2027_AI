Lab 6 — Retrieval-augmented question answering

A system that answers from a fixed document collection and cites what it used — and an evaluation that would catch it when it makes something up.

Dr. Gorkem Kar Due: end of week 14 Weight: 4% of the course grade Pairs permitted, with individual reports

What you are building

A grounded question-answering pipeline over the course's own reading notes — 252 short passages in ../data/lab6/corpus.jsonl. Two stages: retrieve the passages that could answer the question, then answer using only those passages and cite them.

The corpus is small on purpose. With 252 passages, a lexical retriever is competitive and cheap, and you can compare it honestly against a dense one instead of assuming the embedding model wins.

Before you start

  • Module 13 (transformers and language models) and module 14 (perception, robotics, and systems that hold up).
  • AIMA 23–24 for the language-model background, and the evaluation slides from module 11 and module 13.
  • The provided corpus, the 73-question evaluation set (63 answerable, 10 deliberately not), and the answer key that ships with them — all documented in ../data/README.md.
  • Python help for this lab: Hugging Face LLM course and the Sentence Transformers quickstart for the dense retriever. More on the labs page.

Tasks

1. Two retrievers

Implement BM25 over the corpus with your own scoring, and build a dense retriever using embeddings of your choice. The passages arrive already short, so the design question is whether to leave them alone or to merge and re-split them into larger windows — say which you chose and why, because that decision moves recall. Report recall@1, recall@5 and MRR for both, on the evaluation set.

2. Grounded answering

Answer each question from the retrieved passages only, and return the source identifiers you used. The system must be able to say I cannot answer this from the provided documents — the evaluation set contains ten questions that the corpus deliberately does not answer, and answering them anyway is the failure this lab is built to detect.

3. Evaluate the answers, not just the retrieval

Score answers against the answer key on two axes: correctness, and whether every claim is supported by a cited passage. Report the rate of unsupported claims, and the false-answer rate on the ten unanswerable questions. Retrieval recall above 0.9 with a 30% unsupported-claim rate is a worse system than the reverse, and your report should say so in those terms.

4. Failure analysis

Take five failures and classify each: retrieval miss, chunking error, correct passage but wrong synthesis, or confident answer to an unanswerable question. Propose the smallest change that would fix each, and say what that change would cost elsewhere. One paragraph per failure.

Deliverables

  • Code for both retrievers, the answering stage, and the evaluation harness.
  • Results file with one row per question: retrieved ids, answer, score, citation support.
  • Written report, 5–7 pages, including the failure taxonomy.

What the grader runs

python3 qa.py --questions ../data/lab6/questions.jsonl --out results.jsonl

{"id": "q007", "answer": "A common mistake with breadth-first search: ...",
 "citations": ["bfs-pitfall"], "refused": false}

One JSON object per line, in the order of the questions file. The grader scores your file against answers.json on three axes:

  • Answer correctness, 63 questions. A correct paraphrase earns full credit. An answer is accepted when at least 60% of the key answer's content words appear in yours, or when the character-trigram overlap passes 0.45 — so rewording, reordering and light inflection are all fine. An answer that drops a number from the key, or that flips a negation, is rejected however much it overlaps.
  • Refusal, 10 questions. At least 80% of the unanswerable questions must be refused. Answering them is the failure this lab exists to detect.
  • Citation support. At least 70% of your answers must be backed by a cited passage that actually contains the claim.

The matching is lexical, so it rewards using the corpus's own vocabulary — which is what a grounded system should do anyway. It cannot tell a subtly wrong answer from a right one when the words match; that is what the citation check and your own failure analysis are for.

To check yourself before submitting, score your own results.jsonl against answers.json with the three rules above. That is the evaluation harness task 3 asks for, so you will have built it anyway.

Rules

Pairs may build the pipeline together but submit individual reports; both partners must be able to explain the whole system. The syllabus late policy applies: 10% off per day for up to three days, then not accepted. Disclose AI tool use — including whether the answering stage is a language model, and which one, with its version recorded so the result can be reproduced.

Do not use the answer key to tune. It exists for scoring. If your reported numbers cannot be regenerated from your code and the fixed evaluation set, they are not accepted.

Check yourself before submitting

  • Does your system refuse all ten unanswerable questions, or does it answer some?
  • Is every citation a passage that actually contains the claim?
  • Would a reader of your report know which retriever to use, and when?
  • Have you reported variance, or at least run the evaluation twice?
  • Does your failure taxonomy say what each fix would cost?
